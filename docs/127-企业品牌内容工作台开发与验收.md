## 首版实现

| 环节 | 当前行为 |
| --- | --- |
| 平台接入 | `appId=content`、`/t/:tenantKey/content`；同一业务前端、NestJS API、Prisma/PostgreSQL与Worker；运营交付/企业启用沿现有注册器；支持只开通内容应用的企业 |

| 项目与共享 | 需求、受众、渠道、尺寸、变体；企业共享或指定参与人。成员选择使用现有资源选择组件；负责人/内容管理员维护共享范围，应用岗位独立于ERP/CRM/MES岗位 |
| 创作与修改 | 三种内置版式、企业版式保存与版本引用；文字、图片、位置、字号、颜色、锁定图层；直接改字、价格和日期不调用生图；每次修改形成新作品修订 |
| 生成与多尺寸 | 一份产品/变体只生成一张背景，再组合为方图、竖版海报、全屏竖图。初始交付规格1080×1080、1080×1440、1080×1920；是产品预设，不宣称平台官方广告规格 |
| 局部编辑 | Seedream参考图编辑后，由服务端只合成指定矩形区域；先按当前作品尺寸拟合背景，保证选区坐标与预览一致。商品、Logo和关键文字仍是独立图层，不重画商品 |
| 版本与审核 | 版本比较、送审、撤回、通过、退回、待我审核队列；创作者/送审人不能自审。管理员可明确设置免审策略，作品记录操作者和策略版本；新修改不继承旧批准 |

| 团队与用量 | manager/creator/reviewer/viewer岗位、企业图片数上限、单批请求数上限、用量和账单记录；管理员凭供应商账单登记实际费用，更新检查版本并留审计 |
| 回收与运行 | 项目回收/恢复；私有媒体卷；导出包24小时过期清理；业务资料、引用素材和历史版本保留。备份脚本加入内容媒体，但未启用定时器或操作生产停写 |

前端沿公共UI与组件，创作区采用作品条、大预览与图层侧栏；创作模块按路由懒加载。没有整体引入Loomic/Toonflow框架或第二套身份、数据库、队列，参考了其画布/版本及蒙版合成思路后按现有架构实现。

文案首版从核对后的产品事实组成可编辑标题/正文/行动语，也可使用平台现有AI助手获取改写建议；文字助手复用已有文本模型与受控Tool链，Seedream不承担文本对话。图文服务与助手工具调用同一个ContentService，读取来源与授权变化受平台复核。没有为此修改已有应用的AI开关、默认三应用开通政策或聊天试用政策。

## 任务与费用的实际边界

每个生成项先持久化供应商尝试，再发出一次付费POST。Worker使用租约、心跳和条件更新；中断/未知提交不会自动再生图。明确拒绝项可单项重做，同一失败项只建立一个替代批次；成功项不随失败项重跑。客户端保留本次生成确认的请求键，网络结果未知时重试确认仍回到同一批次。

已保存结果可恢复入库；无已保存结果的未知请求由管理员先核对方舟请求/账单并登记依据。本项目有待核实项时暂停新的生成预览。已发生调用但费用尚未对账与“未提交/未消耗”分开，费用未知不写0或自动退款。取消可以停止尚未提交项；已提交请求只能等待并处理回执，不承诺方舟硬取消或退款。

首版治理以生成图片请求数为上限，默认每批12次、每企业每月100次，可由内容管理员调整，交付项最多60个。多尺寸重排不额外计一次生图。尚未做供应商金额自动估价/自动账单同步，生成确认明确显示实际费用待方舟账单核对，不把参考价当实际消耗；管理员可登记账单完成实际费用记录。数量上限不是已测容量或金额硬封顶。

## 真实模型：3次请求，3张图片

| 次序 | 目的与结果 |
| --- | --- |
| 1 | 验证Seedream生图、Worker入库、三规格、版本审核与ZIP。接口成功；成品视觉检查发现模型把提示词内品牌色码画入背景，未作为可用视觉结果外推 |
| 2 | 针对色码问题将自动拼接的十六进制码改为颜色描述，关闭可选水印后仅复测一次。新背景无该色码问题，复用于三规格并完成审核/导出 |
| 3 | 用第2次背景做一次参考图局部编辑。新修订为草稿，旧批准版本保留；选区内变化、选区外像素完全一致，商品/文字图层未改变，草稿导出通过 |

回执合计 `generated_images=3`、`output_tokens/total_tokens=48,904`。Token数是方舟图片接口原始回执，不转换成聊天Token计费；应用计量仍按图片请求记录。没有自动重试、视频调用或多模型对比。已知实际人民币费用为空，待方舟账单核对，不宣称免费或凭公开价捏造实际金额。

## 当前交付边界

本地首版业务闭环已实现并以合成样本做工程及有限真实模型验证。尚未上线、未默认开通企业，未接真实客户品牌资料或取得客户验收；不能据此宣称所有商品、品牌调性或修图效果通过。非矩形蒙版/画笔、完整专业设计器、实时多人同画布、视频、社交发布、自动金额报价与账单同步、按需ERP/CRM Reader均不在当前交付内。

发布时沿现有发布流程：冻结源码与构建证据，联合备份数据库/知识/内容媒体，隔离验证迁移和恢复，核对实际Key权限、私有卷、字体、企业交付/套餐及成员岗位，再发布和回读。回退保留新表、生成尝试、用量与媒体，先停止新提交，不把旧代码回退当作删除已发生请求的授权。

## 构建与现场补充

测试机Docker内存约2GB，标准全量源码构建首次在TypeScript的默认约1GB堆上限失败；提高构建堆上限后的并行尝试因本机内存竞争主动停止，没有将其记为通过。源码已在Node24本机通过类型检查与编译，随后按项目已有`backend-dist`打包方式生成Linux镜像并执行上述运行验收；未调整现有服务运行内存或生产配置。三个API Dockerfile均补上导出所需Noto CJK字体，普通构建命令的堆设置只作用于构建步骤。

新增Content表与迁移的结构核对无Content差异；发现既有MES手工约束/历史索引名称等基线差异，未执行自动删除或修改。恢复归档在全部真实调用后重新生成并再次核验。实际费用仍未凭猜测登记；仅替身测试中的示例账单验证了金额与并发版本控制。
