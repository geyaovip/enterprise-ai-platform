# AI 体验与首阶段 Agent 策略

> 文档属性：功能契约。规则与验收要求不等于全部能力已实现或已发布，日期证据保留其环境。状态入口：[47](47-项目现状与文档维护.md)；公共UI：[ui/00](ui/00-公共UI规范.md)。

## 定位与职责

- **Enterprise AI 是企业级体验入口，不是一种 Agent 类型。**ERP 内助手、业务页面内的分析/草稿、长期任务、洞察和通知也是体验形态；只有真实业务用例才建设相应入口。多入口可复用同一执行能力与治理链路。
- **App 拥有业务，Skill 拥有可评测的专业 AI 能力，Agent 负责任务组织，平台拥有授权和执行治理。**`App ≠ Agent`：App 可以声明 `defaultAgentId`，也可以没有 Agent；`AgentDefinition` 仅描述身份、可用范围和能力引用，不承载 ERP 业务规则。这些是职责边界，不按平台/行业/应用建立三套类体系。
- 首阶段 ERP 客户只有 ERP 可用时，企业 AI 入口与 ERP 内 AI 共用一个 `erp.assistant` 定义和执行链路；会话可分别创建，也可在两个入口打开同一会话。当前 `/t/:tenantKey/ai` 和 `/t/:tenantKey/erp/ai` 共用 API，服务端均构造 ERP 授权上下文；通用 `/apps/:appId/ai` API 已按应用解析 Provider，企业 AI 可视多应用选择器尚未交付，正式目前只显示 ERP。后续企业入口需要清晰展示当前应用和资源上下文；ERP 被停用、用户无权或模型不可用时给出真实状态。
- 后续业务系统启用后不自动创建 Enterprise Assistant。CRM 暂不引入，下一套应用未定。先核对用户是否存在跨应用任务、现有单 Agent 能否在逐 App 重鉴权后组合 Tool；只有确需独立统一编排职责时才增加另一条普通 `AgentDefinition`。Multi-Agent、转交和 Agent 间协议必须由独立工作责任及运行证据证明需要。

## 首阶段必须建立的边界

```text
企业 AI 会话入口 / ERP 内 AI 会话入口
  → 服务端认证并构造可信 RequestContext（Tenant、Member、App）
  → AiProviderRegistry 按已授权 AppContext 解析应用 Agent（ERP 为 erp.assistant）
  → AIExecutionContext（RequestContext + Session + 已核验的当前资源）
  → ERP Skill（场景输入、事实来源、输出规则与样本）
  → 受控适配边界 → OpenClaw Agent/会话/模型执行
  → 已登记 Tool 的执行请求
  → 平台 Tool Executor：目标 App 重鉴权、策略、确认、幂等、审计
  → ERP Native Tool → ERP Application Service → Domain / 同库事务
  → 有权知识查询时：Knowledge Gateway → 当前内置引擎 → 文档版本/Citation
  → 已提交业务回执、来源、用量与审计
```

认证和 App 启用校验先于 Resolver；入口传入的 `agentId`、`appId` 和资源 ID 只表示选择，不授予权限。当前解析为：先按可信 AppContext 取得有权应用 Provider，再使用 `provider.agentId` 或 `${appId}.assistant`；显式 Agent 不匹配则拒绝。Manifest 的默认 ID 是入口声明，不代表已有租户级可配置 Resolver。未提供模型自动路由、独立 Tenant 默认 Agent 或多 Agent 选择器。`defaultAgentId` 不要求每个 App 都配置。企业 AI 与 ERP 内 AI 只在入口带入的上下文不同，解析后必须调用同一执行服务、Tool 执行点和审计链路；页面中纯确定性的 AI 辅助功能不强制包装为 Agent。

`AgentDefinition`、`SkillDefinition`、`ToolDefinition`、`AIExecutionContext` 是服务真实 ERP 场景的代码契约；OpenClaw 负责执行，平台 Tool Executor 仍是统一受控执行点。按场景确定稳定 ID/版本、Owner、允许 App/Tool、输入输出校验、权限、风险、确认、幂等、回执与评测样本。代码定义可继续作为首个 Agent/Skill/Tool 的元数据；D-016 另要求建立企业知识领域、来源与版本，接入 RAGFlow 的摄取/检索并交付 Workspace 知识 UI。Tool 只暴露场景需要的业务能力，不把所有 ERP API 批量转换。

“Skill”应能稳定完成可复用的业务判断或动作，具有明确输入、输出、事实来源、失败方式和评测样本；单条 Prompt 或只调用一次已有 Tool 的包装不应为了命名而建 Skill。首个用例从现有 ERP 的真实业务数据和已授权命令选取，可考虑库存缺料/采购履约；具体选题由业务样本与当前实现决定，不以规划中的供应商风险、3～8 个 Tool 或 2～5 个 Skill 作为数量验收指标。

**首个候选闭环：`erp.purchase_draft_from_text`。**采购人员粘贴真实采购需求，模型提取供应商编号、SKU、数量和备注；ERP 服务核对现有供应商与商品，并明确标出缺失或歧义；用户复核后，才通过 `erp.purchase.create_draft` 创建草稿并返回单号、对象链接和审计。当前已将文字提取移入 `ErpDraftSkill`，经最小 Runtime 调用模型，再经 ERP MasterService 核对引用；ERP 建单页可回填供人工编辑，聊天建草稿也要求逐项预览并确认，过期预览不能提交。**文字提取结果尚不能一键带入聊天的受控动作**，也未用真实模型及固定客户样本验收。若真实客户样本表明该场景收益不足，再在库存缺口处置等已有业务事实中换选一个场景，保留相同验收方法。

当前 `AiService` 注入 `AiProviderRegistry`，按每次请求的 AppContext 解析应用 Provider 和 Agent，不依赖唯一 ERP Provider。应用拥有事实、提示、Tool 和领域 Service；平台负责 Runtime、授权、确认、计量及审计。持久计划由 `TaskService`/公开命令执行，真实模型生成补货计划与业务/知识引用已验证一名生产成员。单据提取仍有自己的 Skill；该场景固定客户样本与人工收益不因其他 Tool 通过自动验收。

### 现有实现的最小迁移

以下 1～5 为 2026-09-30 历史迁移步骤，不再作为重建当前平台的指令。通用注册与 Runtime 链已交付；下一套系统按 [10 接入清单](10-应用接入契约.md#新业务应用接入与验收清单d-029) 增加自身 Provider/Tool，沿用授权、确认与回执链。

1. 先列出 `AiService`、`AppAiProvider`、`ErpAiProvider` 当前职责和调用者，核对平台租户、组织、权限、App 注册及审计的已有实现；只修发现的真实缺口，不重建 Platform Core。
2. 建立可信 Context、代码定义的 `erp.assistant` 和上述 Resolver；先让企业与 ERP **会话入口**解析到同一定义，并共用现有会话/执行服务。无权、停用 App、切换租户和资源上下文过期均须拒绝或重新选择。
3. 从首个采购 Skill 提取可评测的输入、输出、事实来源与失败规则；将当前实际用到的 Tool 声明迁到静态定义和统一执行点。`ErpAiProvider` 可短期作为事实查询/命令的过渡适配，但不再承接新的 Prompt、模型调用、Tool 调度和 ERP 业务规则；逐场景迁出后才判断是否移除。
4. 将现有最小 `AgentRuntime`/Model Gateway 的客户可用调用迁到 OpenClaw 适配边界；当前场景若一次模型调用加受控业务命令就能完成，不强制增加第二次模型调用或多步循环。OpenClaw 只返回建议/Tool 请求，平台执行点负责授权、确认、业务动作和回执；切换后不保留两套写入链。
5. AI 动作保存稳定 ID；ERP 业务命令与动作 ID 关联的审计在同一事务提交。业务成功但 AI 动作回执未落库时，从审计恢复；审计也未发现时保持“结果待核实”，不自动重复执行。会话中断后可重新读取最近操作和恢复消息。下一步用同一组样本验收两个入口、真实模型、持久化业务结果和审计；随后继续 ERP [17 全功能矩阵](17-ERP功能追踪矩阵.md)。

上述步骤是对已有代码的渐进迁移，不要求按建议目录树重排仓库，也不以接口/类的数量作为验收条件。迁移期间只能有一条有权写入路径；过渡适配层的职责和移除条件须在实现记录中明确。

## 授权、风险与业务证据

有效权限是当前成员授权、租户启用 App、对象范围与 Agent/Skill/Tool 允许范围的交集；会话记录、模型输出或 Agent 配置不授予权限。每次查询、异步恢复、Tool 执行与确认均由服务端重新鉴权。模型和 Runtime 不得直读业务表、直接改业务状态或接管业务确认。

读操作可在授权后执行；创建草稿是否需确认由业务影响决定；改变正式业务状态、对外发送或财务/法律动作逐项定义预览、确认/审批和回执。V3.1 的 L0～L4 可作为评审语言，但不能替代现有 Tool 的明确权限及 `confirmationRequired` 行为，也不能以等级名自动放行。输出区分模型建议、业务事实、待确认动作和已持久化结果；证据指向真实且当前用户有权访问的业务对象/版本，过期则重新核对。

## 运行时演进

复杂度按真实需求递进：**单次模型调用 → 确定性流程加模型 → 单 Agent 的受控多步 Tool → 必要时多 Agent**。平台 AI 控制层、权限、Tool 定义、业务确认和审计仍归平台。当前 OpenAI 兼容调用是待迁移现状；D-016 已指定 OpenClaw 为首阶段执行基础，不做多候选选型 PoC，也不强制无业务价值的多步循环。共享云租户与成员隔离、确认后重鉴权及业务回执按 [24](24-首阶段新增能力与验收.md) 验证。

## 首阶段验收增量

在 [02 功能与验收契约](02-功能与验收契约.md) 的 ERP 全功能、聊天操作及 [08 客户上线验收](08-迁移与上线验收.md) 之外，增加以下**目标验证**，并在 [18 实施记录](18-开发与内部验收记录.md) 留证据：

1. 企业入口和 ERP 内入口对同一有权 ERP 场景使用同一 ERP Assistant 定义、执行服务及审计语义；会话 ID 可不同。显式指定无权 Agent、停用 ERP、换企业后不会复用旧上下文。当前路由/接口变化同步更新 [05 路由与接口](05-路由与接口契约.md)。
2. 至少一个真实 ERP 专业能力有固定业务样本：正常、数据不足、过期/冲突、越权和模型失败；记录事实准确性、证据、工具选择与业务时间收益。先由 ERP 人工流程保证结果正确，再检验 AI 是否减少步骤。
3. 至少一个受控写入从建议或草稿进入用户确认、业务 Service 执行、持久化回执；拒绝确认、撤权、超时与重复请求均有明确结果。既有采购草稿和确认链路可作为候选，不为验收虚造新业务对象。
4. 真实模型、真实授权样本、浏览器、API、持久化状态与审计一致后才称客户可用；模拟模型和文档设计只能证明局部路径。

AI 写入若在业务 Service 成功后、动作回执保存前发生超时或进程故障，状态应标为“结果待核实”，通过业务单据或幂等键对账；不能直接报失败或无条件重试。首阶段先用故障注入验证此边界。`AC-18` 只证明首个 Agent/Skill 场景可用，不代替 [17 ERP 功能矩阵](17-ERP功能追踪矩阵.md) 的完整业务范围与 [08 首客试用准入](08-迁移与上线验收.md)。

## 与 V3.1 及后续两轮建议的关系

采纳：多行业定位、企业 AI 作为体验入口、单应用复用 ERP Assistant、Agent 少而精、Skill/Tool 按真实场景建设、能力归属与第二消费者评审、内部 Native Tool，以及先校正边界、随后由 ERP 验证。D-016 进一步直接选定 OpenClaw、RAGFlow 和完整知识产品。保留为后续研究：跨应用 Enterprise Assistant、Multi-Agent、外部 MCP 和多行业治理；不把固定 Tool/Skill 数量、强制多轮模型调用或全部 Phase 原样变为任务。后续业务系统和行业应用按 D-029 另行确定，不固定 CRM/MES/建筑顺序。
