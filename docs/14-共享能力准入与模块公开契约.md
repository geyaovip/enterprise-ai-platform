# 共享能力准入与模块公开契约

> 文档属性：功能契约。规则与验收要求不等于全部能力已实现或已发布，日期证据保留其环境。状态入口：[47](47-项目现状与文档维护.md)；公共UI：[ui/00](ui/00-公共UI规范.md)。

状态：新平台的目标设计与代码评审规则，尚未表示目录或能力已经实现。依据 D-009，以真实应用的复用事实决定业务抽象；平台技术公共能力按首客需求先建设。适用于 ERP、CRM、MES 和后续建筑应用。

## 1. 四种责任范围

| 范围 | 放入条件与所有者 | 首期处理 |
| --- | --- | --- |
| Platform Core | 跨应用一致的租户、身份、会话、应用启用、权限框架、AI 执行、审计与运行基础；平台模块拥有自己的表和接口。 | 只实现 ERP 首客所需的最小可用能力。 |
| Shared Business | 至少两个真实应用需要同一业务事实，并且语义、生命周期、权限模式、数据所有者和事务边界经核对相容。 | 可以为空；不因旧项目存在同名表而预建。 |
| Industry Shared | 同一行业的多个应用确实复用同一业务事实，行业规则不属于 Platform Core。 | 建筑应用启动前只记录候选，不建空模块。 |
| App Domain | 单应用的业务对象、状态、流程、计算、业务权限和 AI 场景；该应用是默认所有者。 | ERP 客户、商机、商品、供应商及交易履约先在 ERP 内建模。 |

四种范围是**归属判断**，不是必须逐级经过的运行依赖链。行业共享模块可直接使用平台接口；应用也可直接使用平台能力。公共模块不能导入某个业务应用的内部代码。平台 AI 通过注册的 Tool 契约调用应用提供的实现，平台只依赖契约，不依赖 ERP 内部服务或表。

## 2. Platform Core 的建设次序

| 首客必须可用 | 由真实用例触发，不预建完整系统 |
| --- | --- |
| Tenant、User、Membership、Session、稳定 `OrgUnit` 与 `MembershipOrg`、可信请求/App 上下文和租户隔离。 | 复杂岗位、矩阵组织、多级管理流程和外部身份供应商；基础组织树及成员归属首期确定。 |
| 代码注册的 App Manifest、TenantApp 启用与服务端权限框架；业务对象范围由所有者再校验。 | 动态 App 定义、任意业务对象/表单/页面生成器、通用工作流与项目级权限引擎。 |
| OpenClaw 执行接入、平台 AI 控制层、目标 App 上下文、Tool 执行、确认、任务状态、用量和审计；RAGFlow 接入与企业知识权限/引用。 | 通用审批平台、无限制的 Prompt/Capability Registry 与第二套向量/模型运行时；高影响 AI 操作的确认不等于通用审批流。 |
| Enterprise Workspace、Tenant Admin、Platform Admin 三个前端、知识空间/文档版本/处理/检索 UI、基础 UI 组件、迁移/备份、健康检查、最小异步任务与可靠重试。 | 无真实消费者的外部连接、通知渠道和定时调度；按场景建设。 |

“归 Platform Core”表示能力所有权；D-016 已明确首阶段须交付 OpenClaw、RAGFlow、完整知识产品和三个前端，其他候选仍不自动纳入。组织单元是企业**内部**管理结构，不是外部客户/供应商 Party；业务对象范围由应用结合组织关系判断。文件、知识、通知和外部集成即使由平台提供基础设施，其合同、图纸、线索提醒等业务语义仍由业务应用负责。所有入口只在对应能力已实现和验收后展示。

## 3. ERP 首期所有权与跨应用演进

- ERP 按 D-008 完整实现旧 ERP 当前已实现的客户、商机、商品、供应商、采购、销售、库存和账款功能。首期 `erp` 模块拥有这些业务表、状态与写命令；对象使用租户内稳定 ID，保留必要的外部标识和来源，不预设 Party、统一 Opportunity 或统一 Item 表。
- CRM 建设时，对照 ERP 客户/商机与 CRM 客户关系、线索转化、联系人、商机的实际语义。相同主体可以通过明确关联引用 ERP ID；语义不同可各自持有对象和 ID。禁止仅凭姓名、企业名或商机标题自动合并。
- MES 建设时，对照 ERP 商品与 MES 物料的实际语义、单位、版本和生命周期。同一物品经确认后可引用或提升为共同目录；不同物品通过显式映射。禁止仅凭 SKU 文本相等合并，或把 MES 计划需求当 ERP 库存。
- 是否提升为共享业务模块在第二个真实使用者出现时评审。若提升，先给出数据迁移、历史引用、ID 映射、权限变化、回退和兼容方案；不能直接搬表或让多个模块共同写同一表。

Q-003/Q-004 是**跨应用关联或共享提升前**的决策门，不阻挡 ERP 自有客户、商机和商品模型开发。ERP 首期仍须先确定自己对象的术语、唯一性、权限、状态和不变量。若首客实际场景要求多个新应用在 ERP 上线当天共用同一对象，应提前关闭对应决策。

## 4. 共享业务能力的提升规则

| 阶段 | 允许的做法 | 进入下一阶段的证据 |
| --- | --- | --- |
| L0 应用内 | 首次出现留在拥有者应用。 | 明确术语、状态、权限、表 Owner 和业务测试。 |
| L1 第二处使用 | 允许局部重复或通过拥有者公开接口使用；先比较事实与流程。 | 两个实际场景及差异清单，不能仅以重复代码行数为理由。 |
| L2 共享候选 | 提出最小共享事实、Owner、消费者、权限、事务和迁移方案。 | 语义、生命周期、权限、数据所有者、稳定 ID 与兼容方案均能说明。 |
| L3 已共享 | 架构评审通过后，才迁入 Shared Business 或 Industry Shared；所有写入仍经唯一所有者。 | 迁移/回退与跨应用回归通过，文档和公开契约同步更新。 |

可复用的纯函数、类型或 UI 原语不必机械等待第二个应用；它们也不能因此变成承载业务规则的“万能 common”。`Party + Role`、统一商机、统一商品目录、建筑 Project 等是候选设计，不是预定表结构。共享提升不要求一定抽到独立服务。

## 5. 模块公开契约与数据所有权

每个模块只公开实际消费者需要的查询、命令和事件；契约写清输入/输出、租户与对象权限、Owner、版本/幂等、错误、事务参与方式和变更兼容期。模块内部 Repository、Prisma Model 和私有应用服务不得被其他模块导入或直接写入。公共包只保存稳定契约，不复制业务实现。

```text
erp/public/     CustomerSummaryQuery、InventoryAvailabilityQuery、PurchaseCommand（按实际需求发布）
erp/internal/   领域规则、Repository、表与事务实现
crm/public/     未来有消费者时再发布客户关系/商机查询
platform/ai/    Tool 契约、调度、权限复核、确认、任务与回执
erp/ai/         注册 ERP Tool 实现，调用 ERP 应用命令
```

以上是边界示意，不要求现在创建空目录或把内部调用改成 HTTP。统一后端内优先使用同进程公开应用服务；采购入库、库存和应付等原子流程保持同库事务。若未来拆分服务，需重新设计事务、一致性、授权传播、超时与回退；公开契约有助于迁移，但不保证“换成远程 API 就无需调整”。

数据库可按模块命名表，是否使用 PostgreSQL Schema 留给实现阶段。每张表必须有唯一写入 Owner；不能建立多个应用都能任意修改的 `shared.common_business_data`。跨模块对象关联保存双方稳定 ID、关联类型和来源，由有权模块维护。

## 6. 前端、AI 能力与配置的共享边界

- `packages/ui` 先沉淀设计 token、Button、Input、Table、Modal 等无业务语义的组件。业务列表、活动时间线、审批面板、AI 洞察卡等先留在应用内，第二处确有相同交互和权限语义时再评审提取；不建设通用页面/表单 Builder。
- 平台 AI 负责模型、会话、Tool 执行、权限与审计，以及有实际复用的文本摘要/结构化提取等基础机制。采购履约、MES 生产异常、建筑合同判断的提示词、事实来源、评测和业务 Tool 归各自应用或经验证的行业模块。不能把领域规则塞进平台提示词库。
- 平台默认值、行业默认值、租户设置、应用设置与用户偏好可以按**具体配置项**定义解析顺序，不建立任意覆盖链。租户或用户设置不得扩大上级安全策略、模型许可、数据访问范围或预算上限；密钥由服务端管理，配置变更留审计。

代码结构从已交付能力逐步形成：统一 `apps/web`（含 Admin）、`apps/api`、`apps/worker`，必要的 `packages/ui` 和公开契约。`shared-business`、`industries/construction/shared`、`packages/business-ui`、SDK 等只在对应模块被评审通过并真实使用时创建。


## D-029 多应用接入与协作实现

1. 后端在组合根注册 `ApplicationRegistry` 的可信 Manifest 和权限贡献函数。注册 ID/权限命名空间匹配；角色仍为当前平台角色，业务授权由各应用贡献。新系统若需新角色体系应另行评审。
2. 应用通过 `CommandRegistry` 发布输入 schema、权限、确认要求和执行函数。执行函数接收事务与新鉴权上下文，通过拥有者 Service 写入自己的数据。公开对象 Reader 核验当前租户与对象权限。
3. 启用 AI 时注册 `AiProviderRegistry`：提示、工具、事实查询和公开命令归应用；成员 Runtime、计量、知识引用和审计由平台复用。每次调用按 AppContext 解析，不共享可变应用实例状态。
4. 前端通过 `registerBusinessApplication` 注册可信构建模块，并匹配服务端 appId/routePrefix。平台运营交付与企业管理员启用是独立步骤；没有可信前端入口的模块不生成可点击工作台菜单。
5. 协作源事务调用 `ApplicationCollaborationService.enqueue(tx,ctx,input)`，源写入和 Outbox 同提交。跨应用最终一致；目标 Service、命令回执及审计同事务提交，幂等标识重复但参数不同则拒绝。不要以 HTTP 重试代替业务幂等。
6. 持续任务保存计划和步骤结果；结构化前置引用只读先前步骤的结果。用户确认不等于 ERP 审批。每次执行、恢复和链接读取重新鉴权；已提交交易取消仍遵守应用领域规则。

隔离测试应用 `qa_lab` 仅在 QA 进程内注册，证明第二消费者、原子回滚、重试、结果回写和对象关联。正式只注册 ERP。ERP 客户/商机等对象继续归 ERP，尚未提升为共享主数据。


## 2026-10-23 MES接入澄清（D-057）

旧段落中的后续应用与“仅ERP”属于原阶段设计。当前电商CRM已发布，MES在工作区实现，状态见47。MES物料目录、BOM、计划、工单和报工归MES所有；同SKU不自动关联ERP商品或库存。本期没有真实ERP-MES协作契约，不提升共享物料域、不写ERP表；已有通用平台能力复用，应用只公开受权对象Reader和确认后创建草稿的命令。见[mes/02](mes/02-数据与接口契约.md)。
