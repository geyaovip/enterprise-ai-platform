## 领域实体

所有 CRM 业务实体使用 `Crm` 前缀、稳定 UUID、tenantId；可编辑对象有 version、createdAt/updatedAt。父子关系用复合租户外键或等效事务校验，不能仅靠子表 tenantId 字段表达隔离。金额采用 Decimal，禁止 JS 浮点作为权威结果；汇总按币种分开。

| 实体 | 必要字段/关系 | 唯一约束与关键索引 |
| --- | --- | --- |
| CrmSettings | tenantId、timezone、metricPolicyVersion、订单口径/窗口、保留设置、dataRevision | tenantId 唯一；策略和版本可追溯 |

| CrmMemberPermissionGrant | membershipId、permission、scopeBindings、active、reason、grantedBy/At、revokedBy/At、version | tenant+member+permission 唯一；只存 06 指定的额外授权，不接受任意权限名 |
| CrmScopeRevision | channelId、sourceRevision、publishedMetricGenerationId、customerRuleRevision、updatedAt | tenant+channel 唯一；归属/标签变化覆盖受影响渠道；与业务提交同事务更新 |
| CrmSalesChannel | tenantId、code、name、sourceType、active | tenant+code 唯一；渠道实例稳定 ID |

| CrmTaskPlanVersion | taskId、planVersion、planText、checklist、origin、aiInvocationId/skillVersion、factReferences、hypotheses、createdBy/At | tenant+task+planVersion 唯一；每次保存变化追加，不覆盖已确认版本；人工修改保留 AI 来源 |

## 状态与关键不变量

- 来源客户唯一键在渠道实例内有效。同名/同手机号不自动合并身份；授权后的人工关联须另设计，V1 不开放自动跨源合并。
- 同一订单及其完整明细在一个事务中应用。重复 sourceRevision+rowHash 不重复写入；相同来源版本不同内容视为冲突，不静默覆盖。
- 已存在订单的渠道、外部订单号和客户关联不可在普通重导中改变；来源纠错若要改关联必须单独预览、复核引用并留审计，不能借更新金额悄悄换客户。
- 一次规则编辑递增 segment.version。任务绑定 evaluation 与成员表；旧规则、新指标或导入不能悄悄改变已确认人群。
- 请求权限和订单来源更新版本均在提交时重查。审计、业务变更及必要 Outbox 在相同事务提交；命令回执与业务状态一起保存。
- dataRevision 在成功提交新业务数据/修正时增加；同时更新受影响渠道的 sourceRevision 或 customerRuleRevision。指标结果整组激活才生成新的 metricGenerationId；查询显示最近成功版本和“待更新”，不能混用。任务确认的依赖向量比较见 04，不因无关渠道的 tenant dataRevision 增加而作废。
- 聚合数据按成员可见客户/渠道范围计算。企业全量 snapshot 不等于任何成员可读的企业合计。

快照 sourceScopeKey 表达实际参与计算的渠道范围；推荐按渠道保存可重建结果，再由 Service 合并当前有权来源并核对策略/时点一致。不能只按 customerId 取全量快照后在前端隐藏渠道名称；授权范围变更必须重取或重算。

## 事务与后台处理

客户批次先提交身份；交易批次把同渠道外部订单号下的订单行与完整明细组成一组，跨文件同事务提交。批次可以部分完成，每一组都有来源、审计和独立计数；重试只处理未提交或可幂等核验的组。批次 completed 只表示导入完成，指标重算另有状态。文件关联/明细完整性和计数守恒见 04。

重算使用版本化结果和短批次提交，整组完成后激活最新可读版本；旧版本保留正在引用的任务和评估证据。租约和失败重试复用平台 Worker 机制，具体处理器在 CRM 注册。

## 迁移与恢复

1. 在隔离数据库添加 Crm 表、索引与约束；不改 ERP 客户/订单主键，不复制旧应用数据库。
2. 新功能默认未交付/未启用；现有租户不默认生成 CRM 授权。只有租户已获交付才可初始化空配置和渠道。
3. 验证迁移后 ERP 原有数量、关联和核心交易不变；新增约束覆盖跨租户外键和唯一键。
4. 发布使用先备份、后 additive migration、再 API/Worker/前端的兼容顺序。回退关闭 CRM 入口，保留新表；不自动 DROP 已有真实 CRM 数据。
5. 联合恢复数据库、受限导入原件和必要加密密钥配置；在独立环境核对批次计数、订单净额、任务人群和审计引用。

批次补偿先预览：仅目标仍处于该批次 afterRevision 时可恢复 beforeSnapshot；若后续人工/来源更新发生，拒绝自动补偿并列冲突。新增客户已被其他订单/任务引用时不能删除，须业务修正；新增订单补偿保留撤销标记和来源。补偿也是新命令、审计和新 dataRevision，不能把历史审计抹掉。实际容量、保留周期及数据库 DDL 在计划确认和样本核对后定稿。

## V1物理实现补充

- 增加`CrmCommandReceipt`统一承载领域命令幂等；`AiComposerDraft`保存按tenant/user/app隔离的加密输入草稿、版本和有效期。
- `CrmMetricSnapshot`按渠道/币种/生成版本保存后台历史净额摘要；窗口R/F/M由RepeatableRead实时SQL计算。后台发布状态不代替当前查询事实，更新中预览不可用于执行确认。
- 人群成员不可变，任务确认冻结evaluation与planVersion；方案局部更新只修改显式提交字段，绑定人群不清空人工方案。
- 当前索引约束和625行新增表迁移为实际实现；未迁入旧CRM或ERP客户表。
