## UI 检查与统一修复

复用 `packages/frontend`，保留现有品牌和三端导航。依据现有控件体系修复：

- 输入、选择框、按钮统一 40px 高、8px 圆角，明确聚焦、禁用和处理中状态；长标签与操作按底边对齐。
- 文件上传不再露出默认浏览器“选择文件”样式，改为有标签和键盘焦点的上传按钮，显示文件/处理状态；仍通过真实文件选择器上传。
- 工具栏、分页、表格行操作、详情按钮/链接和成员设置统一间距；表格横向滚动限定在自己的容器内，页面不整体溢出。
- 桌面面板 24px、窄屏 16px 内边距；双列/表单按断点折叠。短页面移动导航固定 48px，避免网格将按钮拉高。
- 三端移动菜单打开后聚焦导航，限制 Tab 在菜单内，背景内容不可交互；Escape 关闭并返回打开按钮。Workspace、Tenant Admin、Platform Admin 分别检查。采购/仓库/财务的当前导航另行登录复查，回执 `role-navigation-receipts.json`。
- 内部开票、运营执行状态、成员角色和库存来源改为用户可读的中文；工作通道状态不逐字挤成竖排。
- Caddy 对 HTML 设置 `Cache-Control: no-store`；最终 HTTP 响应已核对，避免更新后继续显示旧页面。静态资源按自身路径提供。

## 补齐的业务能力与不变量

### ERP 站内协同

ERP 拥有 Task、Notification、Announcement 和阅读回执；只有 ERP 消费，未提取空的通用协同平台。

- 有权 ERP 成员创建自己的任务；管理员可指派本企业在职成员。任务仅管理员、创建人、执行人可读，跨企业指派拒绝。
- 执行人/管理员完成；创建人/管理员取消或重开。版本检查、状态变更、审计和通知在同一事务；关闭任务不改变采购/销售业务单据。
- 创建请求有幂等键：同键同参数返回同对象，不同参数冲突，并发只写一次任务/通知/审计。
- 通知仅接收人可读或标记已读；采购/销售提交和审核、采购变更、开票处理、收款认领处理产生持久站内通知，不用一次浏览器提示冒充送达。
- 管理员发布/撤下公告，企业 ERP 成员查看并记录幂等阅读回执。正文纯文本。停用成员/ERP 立即阻止访问。
- API：`/erp/tasks` GET/POST、`/erp/tasks/:id/status` POST、`/erp/task-assignees` GET、`/erp/notifications` GET、`/erp/notifications/:id/read` POST、`/erp/announcements` GET/POST、`/erp/announcements/:id/withdraw|read` POST。

### 合同开票与经营责任人

合同详情读取当前有权合同的内部开票申请与登记，展示待处理/已登记/已作废金额和记录；不是税票开具。金额按 Decimal 汇总。

`GET /erp/dashboard/responsibilities` 按当前业务授权分组：商机负责人、待出库合同负责人、待入库采购创建人；展示实际计数及每组最近十条对象链接。销售只见自身业务。库存异常仍到库存预警查看，不编造库存责任归因。

### 商机带入合同

商机页为管理员/销售提供“创建合同”入口，带入客户/商机 ID。合同页重新调用当前授权的客户详情，确认商机仍属于该客户且未输单、客户仍启用，再选择对应项；不沿用 URL 的名称、金额或价格。商品/数量由用户补充，保存仍经原 Sales Service 的当前权限、关联关系和金额计算。

销售浏览器创建 UI-QA-SALES-SO，再将数量 2 改为 3、备注保存成功，canonical 回读版本 2、金额 45 元、商机关联仍一致。无权客户来源拒绝，两个选择保持为空。回执 `output/opportunity-contract-receipt.json`，截图 `opportunity-contract-prefill.jpg`、`sales-contract-edit-final.jpg`。

### 浏览器操作回执

隔离 QA 创建“公开界面验收任务”并完成，完成筛选可回读；发布“公开功能验收公告”并记录已读；查看/读站内开票通知，展开经营责任人关联的合同。真实文件选择器上传公开 Markdown，文档列表回读成功；引擎未开通时明确显示等待状态。

公开业务样本 UI-QA-PO 入库 20 件，UI-QA-SO 出库 2 件后库存 18 件；应付 200 元、应收 30 元，内部开票登记 10 元，到账流水登记 30 元尚未认领。没有实际银行转账或税票交易。

## 真实模型与凭据

火山方舟配置取自用户授权的 Octop 本地配置。实际可用模型为 `doubao-seed-2-1-pro-260915`，地址 `https://ark.cn-beijing.volces.com/api/v3`；旧模型 404，未继续使用。密钥在忽略的受限文件中保存，不写代码、截图或公开文档；平台 Gateway 凭据加密保存。

| 链路 | 实际证据 |
| --- | --- |
| 直接 Ark API | 实际回答 200，并返回 token 用量 |
| 管理员 Workspace API→官方 OpenClaw→Ark | 普通回答，`output/ark-runtime-receipt.json` |
| 真实客户创建 Tool | 创建 canonical 客户 ARK-QA-REAL，`output/ark-tool-receipt.json`；不声称未成功的商品读取 Tool 已通过 |
| 真实采购草稿确认协议 | pending 预览时还没有业务单据→提交预览哈希确认→重复确认，最终恰好一张 ARK-QA-PO-REAL 草稿，`output/ark-confirmation-receipt.json`；是确认协议调用验证，不是人工点击验收 |
| 其余四岗位 | 销售/采购/仓库/财务分别真实回答成功，`output/ark-roles-receipt.json` 及各岗位回执 |

五个 Gateway 使用独立目录、端口和令牌。本机后台进程无生产自动拉起保证。重度镜像构建期间曾超时/取消；后来分别成功，不能把单次成功当成并发容量通过。文字提取、履约分析、复杂 Tool 准确率及 Cloud 检索质量仍需对应样本。

RAGFlow Cloud 无 Key，不使用登录 Cookie 冒充 API 凭据。浏览器规则对创建安全访问凭据要求操作时确认，已明确说明密钥将允许平台管理该账号知识数据；等待答复期间继续完成上述独立开发工作。确认后按 [25](25-首阶段组件部署与联调.md) 完成可用嵌入模型、公开样本和平台完整知识链路。
