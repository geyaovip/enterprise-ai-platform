# 应用接入契约

本契约用于 ERP、CRM、MES 和未来建筑应用。目标是让新应用复用企业公共能力，同时保持自己的业务代码、数据库和发布边界。ERP 是第一个验证者，不为 ERP 编写只适用于它的“平台通用”接口。

## 一个应用要交付什么

| 接入面 | 平台提供 | 应用必须提供 |
| --- | --- | --- |
| 身份与租户 | 登录、会话、成员关系、企业启用状态、服务端请求上下文 | 不建独立账号；所有业务表/查询绑定 `tenant_id`，内部 API 验证签名上下文 |
| 权限 | 权限目录、角色授权、管理员赋权 | 动作清单、对象所有权/状态规则、每个 API 和 AI Tool 的授权检查 |
| 前台 | Shell、企业/应用切换、导航容器、UI token、通用状态组件 | 自己的列表、详情、表单、业务导航和加载/失败/空状态 |
| 管理后台 | 一个 Admin Console、成员与应用管理 | 应用特有的、确有真实功能的管理子页面；不另建后台登录 |
| AI | 可执行操作的聊天框、模型配置、Gateway、任务/用量、Tool 编排、确认与回执协议、权限上下文 | 各模块的上下文 AI 入口、业务提示词、读/写 Tool schema、业务权限、幂等、结果校验与写入规则 |
| 文件/知识 | 存储/检索与租户权限机制 | 业务文档与对象关系、可见范围、引用与过期/重算规则 |
| 审计与运维 | 统一格式、集中索引、请求链路、部署/告警约定 | 业务事务内持久审计/Outbox、模块指标、恢复与迁移脚本 |
| 数据 | 平台库管理身份、授权、应用及共享 AI/文件/知识元数据 | 应用库管理全部业务实体、迁移、备份、业务事务与历史映射 |
| 领域与协作 | 签名上下文、集成事件信封、幂等与链路规范 | 本应用的统一语言、数据所有者、关键不变量、应用命令、跨上下文映射与事件语义；参见[12 领域边界与协作契约](12-领域边界与协作契约.md) |

## 版本化 App Manifest

应用以代码声明稳定 `appId`、显示名称、版本、权限动作、前台路由、后台路由与可用 AI 能力；平台在部署/启动时校验并注册，租户再通过 `TenantApp` 启用。Manifest 只描述已编写的代码模块，不接受客户自定义任意路由或动态表定义。

```ts
type AppManifest = {
  appId: string;                 // 例如 erp，发布后不可随意改名
  version: string;
  platformContractVersion: string; // 应用所需平台契约版本
  permissionActions: string[];   // 例如 erp.purchase.confirm
  webEntry: string;              // 统一 Shell 下的路由前缀
  apiPrefix: string;             // 例如 /api/v1/tenants/:tenantKey/erp
  adminEntries: string[];        // 真实存在的应用管理页面
  aiCapabilities: string[];      // 只有已实现且可验收的能力
  aiToolActions: Array<{          // 聊天与模块 AI 可调用的实际业务动作
    id: string;
    mode: 'read' | 'write';
    confirmationRequired: boolean;
  }>;
};
```

平台可以显示已启用应用、分配权限、统一审计和路由，但不解释应用表单或业务状态。一个租户未启用应用时，前台入口、后台入口、API 和 AI Tool 均不可用。

## ERP 接入时的所有权划分

| 现有 ERP 对象/能力 | 新归属 | 接入要求 |
| --- | --- | --- |
| 旧 `Tenant`、`User`、`Session`、管理员登录 | 平台身份/租户 | 建立旧 ID 到新 `User`/`TenantMembership` 映射；不凭邮箱自动合并身份 |
| ERP 的销售/采购/仓库/财务角色 | 平台授权 + ERP 对象规则 | 动作授予由平台保存；销售私有客户/合同、单据状态等仍由 ERP 判断 |
| 产品、供应商、ERP 客户与商机、采购/销售单据、库存、账款、付款 | ERP 应用库 | 保留业务 Service、事务、版本与唯一约束；平台只引用稳定 ID；不与未来 CRM 的同名实体自动合并 |
| 旧模型密钥设置与一般 AI 会话/用量 | 平台 AI | 密钥迁移需安全流程；会话/用量按租户及应用标识保存 |
| 履约分析结果、缺料建议、单据录入草稿 | ERP | 系统核算与模型解释分开；结果按业务对象版本失效 |
| 旧审计记录 | ERP 保留原始历史；平台建立统一查询索引 | 不改写历史操作者；新写入在 ERP 事务内可靠记录并投递平台 |
| 文件与知识 | 平台服务 + ERP 文档关联 | 只有真实文件用例才启用，现有文字粘贴不自动升级为 OCR |

## API 与事件契约

- 浏览器经平台同源 Gateway 访问应用 API。应用只接受内部签名上下文，不依赖前端传入的租户、角色或用户 ID；响应和错误遵守[05 路由与接口契约](05-路由与接口契约.md)。
- 平台权限检查确认“用户可以尝试此动作”；应用 Service 再确认“此用户可以操作这个业务对象且对象状态允许”。角色变化后下一次请求使用新授权。
- 应用对外发布集成事件时，消息包含 `eventId`、`eventType`、`schemaVersion`、`tenantId`、`sourceApp`、`aggregateId`、`aggregateVersion`、发生时间与 request ID；消费者按 `eventId` 幂等处理。应用内部的领域事件与对外集成事件分开；跨应用事件只表达已完成的事实，不把数据库表暴露成通用事件总线。
- 审计、通知等可延迟投递的副作用用事务 Outbox 保证不丢；库存、账款等 ERP 核心写入在 ERP 本地事务完成，不跨库同步双写。
- 平台聊天和模块 AI 共用 Gateway。聊天中的用户指令可触发已注册的 ERP 读/写 Tool；调用时带原操作者与租户的受限上下文，ERP 每次重新执行对象授权。写 Tool 由业务 Service 持久化并返回对象 ID、状态和回执，平台才能向用户报告“已完成”；超时、冲突和重试不能伪报成功或重复执行。应用既要声明聊天可用 Tool，也要列出模块内 AI 场景及入口。

## 接入检查顺序

1. 梳理应用现有业务、页面、角色、数据与外部依赖；列出统一语言、数据所有者、关键不变量、跨应用同名实体与映射，标注平台共享与应用独有部分。
2. 提交 Manifest、权限动作、路由、后台子模块和 API 契约，并通过平台接入契约测试。
3. 建立应用数据库、租户字段、迁移及身份映射；完成双租户与对象范围测试。
4. 迁入业务命令/Service、API、UI，保持原有业务事务和数值规则；用一个真实纵向切片验证模块协作，不把旧应用独立登录和模型配置复制进新应用。
5. 接入专门聊天并逐模块评估 AI 能力，按真实场景注册 AI Tool、文件/知识和集成；分别验证模型失败、越权、审计与人工业务回退。
6. 通过应用业务验收、共享云部署及专属部署配置检查后，再进行客户试用切换。

后续接入 CRM、MES 时复用同一清单；若第二个真实应用证明某接口不够，再版本化扩展平台 SDK。不能因为 ERP 用到一个工具就将其业务语义提升为全平台规则。
