# 应用模块契约

本契约适用于在统一新项目中开发 ERP、CRM、MES 及后续建筑应用。应用是同一代码仓库、Web、后端 API 和数据库中的业务模块；“注册应用”指声明可用能力，不要求单独建后端、数据库或发布流水线。旧应用仅供需求与规则参考。

## 一个业务模块要交付什么

| 方面 | 公共模块提供 | 业务模块提供 |
| --- | --- | --- |
| 身份、组织与租户 | 统一登录、会话、成员和稳定组织关系、服务端 `AppContext`/`RequestContext`。 | 每个查询/写入按租户、组织和对象范围授权；不另建账号或组织树。 |
| 权限 | 权限目录、角色授予和应用启用。 | 动作清单、领域对象权限、状态和版本校验。 |
| Web / Admin | 统一 Shell、企业/应用切换、UI 组件及管理入口。 | 业务导航、页面、必要的应用管理子页面和完整状态。 |
| AI | 可执行操作的聊天、模型 Gateway、任务、Tool 调度、确认和回执。 | 上下文 AI、提示词、读写 Tool schema、事实来源、业务命令及评测样本。 |
| 文件/知识 | 先定义 `KnowledgeProvider`、`RetrievalContext`、`Citation`；有真实用例时提供存储、处理和授权检索。 | 文档归属、可见范围、来源、版本和失效规则；不得把未实现检索列为已提供功能。 |
| 审计/任务 | 统一格式、查询与幂等 Worker。 | 业务事务内审计/Outbox、模块指标及重试语义。 |
| 数据 | 一个 PostgreSQL 与统一迁移、备份机制。 | 自己拥有的表和字段、业务规则、事务及迁移；其他模块的事实只能通过公开契约使用。 |
| 协作 | 模块公开接口、请求上下文、错误与事件规范。 | 统一语言、不变量、领域命令和跨模块数据需求。 |

## 代码注册的 App Manifest

应用用代码声明稳定 `appId`、显示名称、权限动作、前台和后台路由、已实现的 AI 能力；构建/启动时校验清单与实际代码，租户通过 `TenantApp` 启用。Manifest 只描述现有代码，不产生动态表或页面。

```ts
type AppManifest = {
  appId: string;               // 例如 erp
  version: string;
  permissionActions: string[]; // 例如 erp.purchase.confirm
  webEntry: string;
  apiPrefix: string;           // 同一 API 内的业务路由前缀
  adminEntries: string[];
  aiCapabilities: string[];
  aiToolActions: Array<{
    id: string;
    mode: 'read' | 'write';
    confirmationRequired: boolean;
  }>;
};
```

未启用应用的导航、路由、后台和 AI Tool 都拒绝访问。Manifest 不等于独立服务发现或远程插件机制。

`appId` 在 [03 架构契约](03-架构与数据安全.md)的 `AppContext` 中由服务端核验，不只是路由前缀。每个模块的 API、后台页面、Tool、知识检索与审计都携带该上下文；同一用户切换应用后按新上下文重新授权。

## ERP 新建时的所有权

| 对象/能力 | 所有者与开发方式 |
| --- | --- |
| 企业、用户、成员、稳定组织关系、登录、应用启用 | 平台公共模块一次建设，ERP 直接复用；销售负责人和对象范围由 ERP 业务规则解释。 |
| 客户/伙伴与商机 | 新 ERP 首批拥有并实现旧 ERP 当前已实现的客户与商机功能，持有 ERP 稳定 ID 和写入规则。未来 CRM 依据 Q-003 决定公开契约引用、显式关联或评审后提升共享；不在平台 P0 预建业务表。 |
| 商品/物料基础目录 | 新 ERP 首批拥有并实现旧 ERP 当前已实现的商品功能，持有 ERP SKU/ID、价格与库存规则。未来 MES 依据 Q-004 决定公开契约引用、显式关联或评审后提升共享；不在平台 P0 预建业务表。 |
| 采购、销售合同、库存、应收应付及收付款 | ERP 模块拥有业务表、命令、事务和审计；按 D-008 重新实现旧 ERP 当前已实现的完整范围。 |
| 模型密钥、一般对话、任务与用量 | 平台 AI 模块统一管理。ERP 提供业务提示词、Tool、分析和草稿能力。 |
| 业务文档 | 平台存储/知识能力与 ERP 对象关联；只启用已开发且验收的文件能力。 |

## 模块调用、API 与事件

- 浏览器访问统一同源 API。API 入口从会话、Membership 与 TenantApp 构造可信 `AppContext`/`RequestContext`，校验租户、组织关系、应用启用和动作授权；ERP 等业务模块再次校验对象范围、状态和版本。不信任前端传入的用户、角色、租户或 appId。
- 同进程模块通过公开应用服务接口协作，不直接操作其他模块拥有的表或复制规则。需要原子性的业务写入可在同一数据库事务内协调；只有确有异步需求的副作用才用 Outbox/Worker。模块内部领域事件和向外部系统发布的集成事件分开。
- 统一 AI 聊天与模块 AI 通过已注册 Tool 调用相同的业务服务。写入返回对象 ID、持久化状态和回执；超时、冲突或重试不能伪报成功或重复执行。
- 外部 API 和事件按版本管理；内部模块接口随同一代码版本演进。业务 API 的 schema 由所有者模块维护，共享包仅沉淀真正跨模块稳定的类型。
- 只有外部系统或外部 AI 接入才考虑 HTTP/Webhook/MCP 适配器；内部应用与平台不经 MCP 或回环 HTTP 协作。AI 控制层和 Model Gateway 的分工及未来 Runtime 准入见 [ADR-002](ADR-002-AI运行边界与外部协议.md)。

### Public Contract 的最小内容

模块有真实消费者时才公布所需查询或命令，例如 ERP 的 `CustomerSummaryQuery`、`InventoryAvailabilityQuery`。契约记录 Owner、输入输出、租户与对象授权、版本/幂等、错误和事务参与方式。实现留在 `erp/internal`；CRM、MES、平台 AI 不导入 ERP Repository 或直接写 ERP 表。平台 AI 仅持有 Tool 契约，ERP 注册 Tool 实现并调用自己的应用命令。公开契约和业务共享的提升评审见 [14 共享能力准入](14-共享能力准入与模块公开契约.md)。

同进程公开服务是首期实现方式，不要求远程 API。以后独立部署某模块时，授权传播、同库事务、超时、重试和一致性都需要重新设计，不能只替换调用地址。

## 新业务模块开发顺序

1. 参考旧应用与真实客户场景，重新确定本模块功能、角色、术语、对象所有者和关键业务不变量；列出可复用的公共能力。
2. 先由本模块拥有自己的业务事实，定义稳定 ID、应用命令、权限和事务；出现真实跨应用消费者时，比较语义并决定公开查询/命令、显式关联或经评审提升共享。不得复制平台登录或模型设置。
3. 注册 Manifest、路由、后台入口和 AI Tool，使用统一 Web、API、数据库迁移和 CI。
4. 实现一个可验证的真实纵向流程，覆盖跨租户、越权、并发、失败恢复和业务回执；旧代码只作为行为参考，不做搬迁步骤。
5. 逐模块实现有业务价值的上下文 AI，使用真实模型和授权样本验证；完成共享云客户试用准入，并检查同一构建可按配置用于专属部署。

ERP 是首个验证统一架构的业务模块。CRM、MES 开发时复用同一平台技术能力和开发契约；第二个真实业务场景出现后，按 [14 准入规则](14-共享能力准入与模块公开契约.md) 评估共享业务能力，不因代码相似自动抽取。

## 后续标准应用的能力来源设计

设计 CRM、MES 和建筑等后续应用时，逐项说明业务能力的边界，不把“开箱即用”理解为重做所有外围系统。这里的独立运行指**未连接客户已有业务系统时，应用仍能完成自己的核心业务闭环**；应用仍运行在统一平台、Web、API 和数据库中。

| 类别 | 判断标准 | 默认做法 |
| --- | --- | --- |
| Core Native（应用核心） | 构成该产品的主要业务事实、不变量和闭环。 | 应用自己拥有模型、命令、权限与验收；外部系统可提供输入，但不能悄悄代替核心规则。 |
| Built-in Basic（内置基础） | 核心闭环必须用到，而客户未必已有对应系统。 | 在本应用或已有明确 Owner 的模块内提供够用的基础能力，不复制完整外围产品。 |
| External Optional（可接外部） | 客户已有成熟系统，且该项事实确有来源替换需求。 | 有确定的客户场景时，经拥有者公开契约和按需建设的 Integration Adapter 接入；未接通时继续使用已验收的内置来源。 |

“内置/平台内其他应用/客户外部系统”是**某一项能力的来源选择**，不是通用 `Customer`、`Contract`、`Project` 等大一统数据模型。只有出现真实替换需求时，才定义该能力的最小查询/命令接口、对象 ID 映射和适配器。配置只在实现并验证相应来源后开放；`App Manifest` 可以描述代码已支持的能力，租户的具体来源绑定由服务端配置管理，不能让 Manifest 直接变成任意连接器或业务表生成器。

每项可替换来源在实施前须明确：权威数据源与写入 Owner、字段语义与版本、租户和对象授权、外部身份/ID 映射、同步或实时读取方式、不可用时的行为、切换/回退及历史引用。一个业务事实不能因两个来源并存而被无意双写；外部来源失效时不得静默改读内置旧数据并呈现为最新事实。页面和 AI Tool 使用同一有权来源与应用命令，回执与审计记录实际来源。外部 HTTP/MCP 是适配协议，内部调用仍遵循 [ADR-002](ADR-002-AI运行边界与外部协议.md) 的代码级公开契约。

本节是**后续应用的设计准则**，不变更新 ERP 按 D-008 完整重做旧 ERP 已实现功能的范围，也不要求现在建设通用 Integration Runtime、MCP Server、全量来源切换后台或空 Provider 接口。进入具体应用设计时，再用真实客户场景逐项确定 Core Native / Built-in Basic / External Optional。

## 后续新应用的 AI 业务闭环

依据 [D-012](00-文档索引与决策记录.md#已确认的决策)，后续新应用先选定具体客户、角色和需要解决的业务结果，再设计 AI 参与的工作链路。聊天、摘要、检索或生成草稿可以是步骤，但不能代替业务结果的验收。应用既可以使用自己的业务事实，也可以在已授权、已验证的场景中使用平台内其他应用或客户已有系统的事实；这不要求客户购买我们的 ERP，也不意味着新应用变成平台之外的独立服务。内部模块继续通过公开代码契约协作，外部连接按上一节逐项建设。

每个候选闭环至少写清以下内容，并以真实业务样本验证：

| 环节 | 设计与验收问题 |
| --- | --- |
| 发现 | 哪个业务变化或资料触发检查？确定性条件由业务代码计算，AI 只对需要解释或识别的内容给出候选判断；记录触发时间、来源和版本。 |
| 核对 | 候选判断依赖哪些可访问的单据、资料和引用？缺失、过期或相互矛盾的数据如何标记？误报、漏报如何由有权人员反馈？ |
| 行动 | 谁负责判断，哪些动作可自动生成草稿，哪些必须预览并明确确认？写入仍经所属应用命令、权限、状态/版本校验和幂等处理。 |
| 跟踪与关闭 | 应用拥有什么业务状态、责任人、下一步、期限（仅在有可靠数据时）、完成条件和回执？来源变化、动作失败或撤权后如何重算、恢复或停止？ |
| 效果 | 对照原人工流程，记录发现覆盖、误报/漏报、处理耗时和实际关闭结果；指标定义与目标值由客户场景确定，不能用模型调用次数或页面数量代替。 |

由 AI 发现的潜在变更、经营风险或待办，若需要跨请求跟踪，应作为**所属应用**拥有的候选业务状态建模，保留来源、证据、负责人、确认人与状态历史。模型建议与已核实事实分开；外部函件、金额、合同权利判断等高影响事项经有权人员复核，不能因模型输出自动成为已确认结论或对外承诺。平台负责身份、AI 执行、审计及必要的技术能力，不预建通用 `AIInsight`、行业事件表或万能审批流。

例如未来 AI 项目经营可从获授权的会议纪要或指令中识别潜在变更，列出合同依据与缺失证据，交项目商务人员确认后建立 `ChangeEvent`，继续跟踪通知、签证及处理结果。具体资料接入、条款判断和流程须在进入建筑阶段时依据真实客户样本单独评审；本例不是当前已交付能力或固定 V1 清单。

合同分析、变更识别等行业 AI 能力的提示词、评测和业务规则先留在首个拥有者应用；第二个真实消费者出现后，再按 [14 共享能力准入](14-共享能力准入与模块公开契约.md)比较语义与权限，决定是否沉淀到 Industry Shared。通用模型调用、Tool 调度和审计仍由平台统一提供。该准则不改变当前 ERP 首客范围及既定开发顺序。
