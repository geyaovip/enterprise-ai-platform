## 已确认的决策

| ID | 决策 | 影响 |
| --- | --- | --- |
| D-001 | 建设共享企业 AI 平台；业务应用用普通代码开发，不做通用低代码 APaaS。 | 平台/应用边界与技术选型 |
| D-002 | 先建平台，再接入现有 ERP、CRM、MES，之后开发建筑行业应用。 | 路线图替代原草案的建筑先行顺序 |
| D-003 | ERP 是首个真实客户试用应用；没有“内部演示版”交付目标。 | 验收、模型质量、运维和安全均按客户试用要求设计 |
| D-004 | 首批采用共享云服务，架构考虑客户专属部署。 | 租户隔离、配置与基础设施抽象 |
| D-005 | 新平台接入并验收三套应用后，才考虑移除旧项目。 | 迁移和回滚期间旧系统必须保留 |
| D-006 | 先设计、开发可供未来应用复用的整体平台架构；ERP 接入时判断哪些能力复用平台、哪些留在 ERP。目标不是合并三套旧后端和数据库。 | 平台核心、应用接入契约与数据所有权先于旧应用改造 |
| D-007 | 平台提供可通过受控 Tool 执行业务操作的 AI 聊天框，而不只是问答；适合的业务模块也尽量嵌入上下文 AI 能力。 | 对话操作与模块 AI 共用权限、业务 Service 和审计；逐场景定义可执行动作与验收 |

## 本轮架构设计

以下是依据 D-001～D-007 作出的**目标设计**，供实施和评审使用，不应写成已经上线的事实：

| ID | 设计选择 | 依据 |
| --- | --- | --- |
| A-001 | 平台核心内部用模块化单体；每个 Code-native 应用拥有独立业务服务和数据，统一 Web/Admin Shell 与同源 Gateway。 | 公共能力只建一次，业务模型保持边界，便于未来应用和专属部署。 |
| A-002 | 平台库保存身份、成员、授权、应用启用及共享 AI 等元数据；应用库保存自己的业务数据，使用独立凭据和迁移。可共用 PostgreSQL 集群。 | 不把“合并数据库”当复用手段，保留本地业务事务。 |
| A-003 | 应用通过版本化 Manifest、平台 SDK、签名请求上下文、AI Tool 与审计/事件契约接入。 | 新应用无需重建登录、权限基础、AI 网关和管理后台。 |
| A-004 | 先以平台身份/应用目录/AI、ERP、CRM、MES 的领域边界确定模型所有者；ERP 采购、库存和账款首期保持同一业务事务边界。 | 关键业务不变量保持原子性，避免为套用 DDD 拆出大量进程。 |
| A-005 | 跨应用使用显式身份/主数据映射、业务 API 或可靠集成事件；相同名称不代表同一业务实体。 | CRM 客户与 ERP 客户、ERP SKU 与 MES 物料各有语义，跨应用不直连数据库。 |
| A-006 | AI 聊天与页面共用应用命令和领域规则；模型负责理解意图，应用负责授权、执行、事务和回执。 | 可让 AI 实际办事，同时防止模型文本冒充成功或绕过业务约束。 |

## 文档维护规则

- 一项产品决策只在本文件登记一次，相关文档引用其 ID，避免出现相互矛盾的“事实”。
- 功能用稳定编号（如 `PL-01`、`ERP-01`），验收用 `AC-` 编号；代码和测试可引用相同编号。
- 变更权限、数据或客户试用范围时，先更新决策和验收，再修改实施细节。
- 文档审查、代码通过、真实客户试用是三个不同的验证层级，记录时不得混用。
