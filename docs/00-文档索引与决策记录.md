## 本轮架构设计

以下是依据 D-001～D-011 作出的**目标设计**，供实施和评审使用，不应写成已经上线的事实：

| ID | 设计选择 | 依据 |
| --- | --- | --- |
| A-001 | 一个 Monorepo、统一 Web/Admin、一个模块化后端 API、一个 PostgreSQL 数据库及独立 Worker；平台和业务应用是同一产品内的代码模块。 | 公共能力直接复用，首期不预设每应用独立服务或数据库；同一构建可按租户启用模块并用于专属部署。 |
| A-002 | 平台与业务模块各自拥有数据表、迁移和业务规则；统一数据库按模块限定写入所有者。必须原子完成的同库业务操作使用事务。 | 统一物理架构不等于任意模块读写别人的表；保留领域不变量和清晰归属。 |
| A-003 | 模块以代码注册 Manifest、权限、路由、AI Tool 和审计契约；同进程通过应用服务接口协作。仅在真实扩容或隔离需要出现时拆分运行单元。 | 新应用无需重建登录、权限基础、AI 网关和管理后台，也不必另建独立 API。 |
| A-004 | 先以平台身份/应用目录/AI、ERP、CRM、MES 的领域边界确定模型所有者；ERP 采购、库存和账款首期保持同一业务事务边界。 | 关键业务不变量保持原子性，避免为套用 DDD 拆出大量进程。 |
| A-005 | ERP 首期拥有自己的客户、商机、商品和供应商业务模型。CRM/MES 出现真实复用时比较语义和生命周期；同一业务对象经评审可提升共享，语义不同则显式关联稳定 ID。 | 不因旧项目的同名表提前建立统一 Party、商机或商品目录，也不让未来应用决定阻挡 ERP 自有模型。 |
| A-006 | AI 聊天与页面共用应用命令和领域规则；模型负责理解意图，应用负责授权、执行、事务和回执。 | 可让 AI 实际办事，同时防止模型文本冒充成功或绕过业务约束。 |
| A-007 | 模块只经拥有者的公开契约协作；平台 AI 通过注册 Tool 调用应用实现。业务共享按 L0～L3 准入与迁移规则提升；数据库表有唯一写入所有者。 | 保持模块化单体的清晰边界，避免 `shared` 成为任意写入的公共库；详见 [14 准入规则](14-共享能力准入与模块公开契约.md)。 |
| A-008 | `AppContext` 是服务端可信的应用授权上下文，组织归属是平台稳定关系；知识检索接口复用相同的租户、成员、App 与对象范围。 | 每次请求和 AI Tool 重新鉴权；知识和文件实现仍按真实用例建设。 |

## 文档维护规则

- 一项产品决策只在本文件登记一次，相关文档引用其 ID，避免出现相互矛盾的“事实”。
- 功能用稳定编号（如 `PL-01`、`ERP-01`），验收用 `AC-` 编号；代码和测试可引用相同编号。
- 变更权限、数据或客户试用范围时，先更新决策和验收，再修改实施细节。
- 文档审查、代码通过、真实客户试用是三个不同的验证层级，记录时不得混用。
