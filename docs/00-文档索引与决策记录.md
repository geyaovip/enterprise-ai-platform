## 当前开发收尾口径（D-022）

- 当前生产使用内置 PostgreSQL + pgvector 知识库，包含混合检索、结构分块、本地规则重排序及中英文 OCR。RAGFlow Cloud 是暂缓的可选接入，不作为当前知识产品完成条件。
- 当前工程证据：一名成员已开通生产 Runtime 并通过真实模型/Tool/内置知识联合验证，ERP 完整性及增量流程已有正式多账号写入回归。其他成员配置、容量、外部值守通知和实际线上入口回退仍需各自验收；当前结果见 [41](41-六批优化交付与线上验收.md)。
- 生产定时备份暂缓；已有手动数据库＋知识原件联合备份和独立恢复证据继续保留。真实客户数据、业务规则、打印模板及资料质量测试由用户后续安排，不与本轮工程完成状态混写。
- “成员 AI 执行环境绑定”指平台运营将有效成员关联到其独立 OpenClaw Gateway 地址、加密访问凭据及助手标识。平台按当前成员选择执行环境；每次 Tool 调用仍由平台重新鉴权并经过业务 Service。知识引擎按企业配置，两者分别开通。

历史 V3.1 规划及后续 GPT 建议的 AI 体验范围见 [22](22-AI体验与首阶段Agent策略.md)；V3.6.1 两份规划的初次评审及用户后续修订见 [23](23-V3.6.1规划采纳评审.md)。规划文字本身不是决策；**D-016 是用户本轮直接确认的新增范围和技术选择**，不再按 D-015 的候选选型门槛处理。

## 本轮架构设计

以下是依据上述决策作出的**目标设计**，供实施和评审使用，不应写成已经上线的事实：

| ID | 设计选择 | 依据 |
| --- | --- | --- |
| A-001 | 一个 Monorepo、三个独立前端（Enterprise Workspace、Tenant Admin、Platform Admin）、一个模块化后端 API、一个 PostgreSQL 数据库及独立 Worker；平台和业务应用是同一产品内的代码模块。 | D-016 更新前端交付形态；三端共享设计与 API 契约，不复制 ERP 领域规则，不预设每应用独立服务或数据库。 |
| A-002 | 平台与业务模块各自拥有数据表、迁移和业务规则；统一数据库按模块限定写入所有者。必须原子完成的同库业务操作使用事务。 | 统一物理架构不等于任意模块读写别人的表；保留领域不变量和清晰归属。 |
| A-003 | 模块以代码注册 Manifest、权限、路由、AI Tool 和审计契约；同进程通过应用服务接口协作。仅在真实扩容或隔离需要出现时拆分运行单元。 | 新应用无需重建登录、权限基础、AI 网关和管理后台，也不必另建独立 API。 |
| A-004 | 先以平台身份/应用目录/AI、ERP、CRM、MES 的领域边界确定模型所有者；ERP 采购、库存和账款首期保持同一业务事务边界。 | 关键业务不变量保持原子性，避免为套用 DDD 拆出大量进程。 |
| A-005 | ERP 首期拥有自己的客户、商机、商品和供应商业务模型。CRM/MES 出现真实复用时比较语义和生命周期；同一业务对象经评审可提升共享，语义不同则显式关联稳定 ID。 | 不因旧项目的同名表提前建立统一 Party、商机或商品目录，也不让未来应用决定阻挡 ERP 自有模型。 |
