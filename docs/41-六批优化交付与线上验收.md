## 六批交付

| 批次 | 已实现与验证的结果 |
| --- | --- |
| 1：多应用与 AI 边界 | 可信应用注册、独立权限贡献、按请求解析的 AppContext/AI Provider、通用 AI 路由；平台授权不再通过直接读取 ERP 表取得。成员 Runtime 实际绑定，真实模型创建客户并产生业务回执。 |
| 2：持续任务 | 九条独立 Worker 通道；持久计划/步骤、确认、审批等待、重试、取消、租约和崩溃回执修复；并发幂等与租户轮转。暂停知识通道 20 秒时，业务任务仍完成。 |
| 3：补货闭环 | 根据真实库存、未发货销售需求和未入库采购量计算；展示供应商、商品、数量和实际单价，保存快照并拒绝过期依据。计划确认→采购草稿→提交→指定负责人审批→分批入库→结果核验在线上走通。 |
| 4：经营事件 | 缺货、采购延期、应收逾期、应付逾期；真实来源、去重、岗位负责人、转交、处理、逾期升级及来源恢复后自动关闭。四类事件均在线上生成并解除，待办完成、解除通知发出。 |
| 5：应用协作 | 公开命令与对象 Reader、事务 Outbox、目标业务回执、结果回写、关联对象及双端权限复核。隔离第二应用验证原子回滚、重复交付、失败重试、权限撤销和跨租户拒绝。 |
| 6：商业与支持 | 套餐、快照订阅、成员/AI/任务/知识额度服务端阻断、用量与已知成本；人工账单和凭证留痕。企业管理员审核限时支持访问，按范围读取摘要，过期和撤销立即失效；三端页面及操作闭环上线。 |

补货当前目标为警戒值以上一个基础单位，建议数量扣除在库和在途、加上未发货需求；并非模型预测采购量。用户确认计划与企业业务审批分别记录，AI 无权代替指定审批人批准单据。

## 后续应用接入方式及交付边界

新系统需实现自己的可信 Manifest、角色权限贡献、业务 Service、命令/Reader、前端注册入口；需要 AI 时注册自己的 Provider/工具，再由平台运营交付、企业管理员启用。跨应用只调用拥有者公开契约，结果通过回执/对象关联获取；原子业务留在所属应用同库事务，跨应用事件采用最终一致性。实际接入清单见 [14](14-共享能力准入与模块公开契约.md)。不需要另写一套租户、任务、计量和支持后台。

- CRM 不引入；旧三应用不迁入新代码，ERP 客户/商机仍归 ERP。共享主数据的语义及数据迁移需在真实第二系统确定后评审。
- 当前仍为代码开发的模块化单体，未建设任意上传代码、低代码生成或自动安装外部应用的 Runtime。
- 当前角色体系是现有固定角色；新系统需要新角色时另行扩展。任务按租户轮转和租约领取，未宣称任意多实例或高并发容量已验收。
- 经营事件当前每分钟分批扫描，最多每批 20 个租户；完整发现/解除延迟随启用租户数变化，不能理解为业务提交后即时扫描。默认 24 小时升级提醒。
- 成本根据真实返回 Token 与配置单价快照计算；缺失用量或价格保持未知，不冒充供应商实际账单。支付网关未接通，人工收款只由实际凭证登记。
- 支持访问最长 8 小时，仅限批准的运行、任务状态或审计摘要；不提供客户正文、任务输入结果、账号或密钥。
- RAGFlow Cloud、生产定时备份、真实客户场景继续暂缓。飞书/钉钉外部授权及值守通知未开通，ERP 内通知与流程闭环已验证。
